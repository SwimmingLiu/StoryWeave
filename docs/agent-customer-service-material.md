# Agent 客服材料稿件

> 受众：客服负责人、产品团队、运营团队与信息安全团队  
> 用途：用于内部讨论、方案评审和首期试点设计  
> 资料口径：本文把官方文档和法规中的事实、对产品能力的概括、实施判断和待验证事项分开标注。文中的示例是说明流程的假设，不是客户案例。  
> 资料更新时间：2026 年 8 月 20 日

## 摘要

Agent 客服是一类能够处理服务任务的 AI 系统。它需要理解用户的目标和上下文，检索受控的业务知识，按照权限调用业务工具，检查动作结果，再向用户说明结果；当身份、规则或结果存在不确定性时，它应当把上下文和已完成的步骤交给人工继续处理。

它与只返回固定答案的 FAQ、只匹配意图的聊天机器人、只执行预设脚本的 RPA 都有交集，但边界不同。Agent 客服的价值不在于把回复写得更像人，而在于把一次服务请求推进到可验证的结果。能否推进，取决于知识是否可用、工具是否安全、权限是否明确、失败是否可恢复，以及每一步是否留下可检查的记录。

首期不宜从“让 Agent 处理所有客服问题”开始。更稳妥的范围是选择一条高频、规则相对稳定、结果可验证、风险可控制的流程，先把受理、检索、执行和转交完整跑通，再根据评估结果扩展知识、工具和渠道。

## 1. Agent 客服是什么

### 1.1 一个可操作的定义

本文把 Agent 客服定义为：

> 在客服渠道中，能够围绕服务目标进行多步处理，使用受控知识和业务工具完成或推进任务，并在超出边界时转交人工的 AI 系统。

这个定义包含五个动作：

1. **理解目标**：识别用户要解决的事情、对象、约束和紧急程度，而不是只识别一个意图标签。
2. **获取依据**：从版本明确、权限匹配的知识源中查找规则、政策、产品状态或操作说明。
3. **执行动作**：通过结构化工具读取或修改业务数据，例如查询订单状态、创建服务工单或安排回访。
4. **校验结果**：确认工具返回了什么、动作是否成功、结果是否与用户请求一致，并记录失败原因。
5. **交付或转交**：向用户给出可核对的结果；若需要人工处理，则传递会话、身份、知识依据、工具调用和剩余问题。

OpenAI 的 Agents 文档将 agents、工具、编排、护栏、人工审批和结果状态分别作为开发能力；这说明“会生成回复”只是系统的一部分，而不是完整的服务能力。[1][2][3]

### 1.2 与相邻方案的区别

| 方案 | 主要工作方式 | 能否自主推进任务 | 典型限制 |
| --- | --- | --- | --- |
| FAQ 或知识库 | 用户查找文章，或系统返回匹配答案 | 通常不能 | 需要用户自己完成后续操作；内容更新和命中范围影响很大 |
| 规则型聊天机器人 | 按意图、槽位和流程节点匹配 | 只能推进预先编排的路径 | 遇到表达变化、条件冲突或流程外问题容易中断 |
| RPA | 按固定脚本操作页面或系统 | 可以执行固定动作 | 不负责理解开放式目标；页面、字段或流程变化会影响脚本 |
| Agent 客服 | 理解目标，检索依据，选择工具，检查结果 | 在授权范围内可以 | 需要治理模型输出、工具权限、数据访问、失败和人工转交 |
| 人工客服 | 结合经验、政策和业务系统处理 | 可以处理复杂例外 | 成本、排班、培训和跨系统操作能力受组织条件影响 |

这张表是方案边界的概括，不是对每家产品的功能分级。一个产品可能同时提供知识库、规则机器人、Copilot 和 Agent；实际能力应以具体版本、配置和权限为准。Microsoft 的 Contact Center 文档同时列出面向客户的 Agent、面向坐席的 Copilot 和服务运营 Agent，正说明这些形态可以共存，不能只按产品名称判断能力。[4][5]

## 2. 客服请求为什么需要任务视角

用户常用一句话描述需求，但服务系统要处理的是一串动作。例如，用户说“我的包裹还没到，能不能改到公司地址”，至少涉及：

- 确认用户和订单身份；
- 查询订单、物流和配送状态；
- 判断是否已经进入不可修改阶段；
- 根据地址变更规则判断能否执行；
- 必要时校验新地址；
- 调用修改或创建人工工单的工具；
- 向用户说明修改成功、失败或等待人工处理的原因。

上面是一个**假设示例**，不代表任何企业的真实流程。它的作用是说明：客服问题的难点通常不在生成一句话，而在于保持上下文、遵守业务条件，并把动作结果交付给用户。

把请求看成任务后，系统设计需要回答四个问题：

1. 任务的完成条件是什么？是返回一条说明，还是业务系统出现一个可验证的状态变化？
2. 哪些信息必须先确认？哪些字段缺失时只能追问，不能猜测？
3. 哪些动作可以自动执行？哪些动作必须经过用户确认或人工审批？
4. 失败后如何继续？是重试、补充信息、撤销动作，还是带着完整上下文转交人工？

## 3. 一次服务请求的完整流程

为了便于设计和评估，可以把一条服务请求拆成四个阶段。

### 阶段一：识别目标和边界

系统先确定用户要达成的结果、涉及的对象和必要条件。它应当区分“我想了解退款政策”和“请帮我发起退款”，也应当发现订单号、身份信息或授权状态是否缺失。

这一阶段的输出不是一句自然语言回复，而是一个可检查的任务状态，例如：目标为“查询退款进度”，对象为“订单 123”，身份校验已完成，尚缺“退款申请编号”。如果目标本身存在多种解释，应先追问，不要直接调用写入工具。

### 阶段二：检索知识和业务上下文

知识检索应当优先返回与当前产品、地区、时间和客户类型匹配的内容。知识条目需要有来源、版本、有效期和责任人；过期、互相冲突或权限不匹配的条目不能直接作为依据。

OpenAI 的 file search 文档把“先搜索文件，再生成回答”作为一种工具工作流；在客服系统中，可以把同一原则扩展为企业知识库、政策库、订单数据和会话上下文的分层检索。[6]

检索结果不等于事实。系统还要记录使用了哪些资料，必要时把来源名称或政策版本呈现给坐席和用户。对于退款金额、合同条款、医疗或金融建议等高风险内容，知识来源和人工复核要求应当更严格。

### 阶段三：调用工具并校验结果

工具调用是 Agent 客服区别于纯问答的重要部分。OpenAI 的 function calling 文档说明，模型可以通过结构化函数参数连接外部数据和系统；工具本身仍由应用侧定义、鉴权和执行，不能把模型输出直接当作业务操作。[7]

每一个工具都应明确：

- **用途**：是查询、预览、创建、修改还是取消；
- **输入**：字段类型、必填条件、格式、取值范围和敏感字段；
- **权限**：哪些角色、渠道和身份状态可以调用；
- **副作用**：是否会产生费用、通知、状态变化或不可逆影响；
- **结果**：成功、失败、部分成功和需要人工处理分别如何表达；
- **重试**：如何避免网络重试造成重复扣款、重复建单或重复发消息。

对有副作用的动作，可以先执行“预览”，把将要改变的对象、范围和结果告诉用户，再要求确认。对不可逆动作或高风险动作，应当设置人工审批。OpenAI 的 Agents 文档把 guardrails 和 human review 作为受控工作流的一部分；Salesforce 的 Agentforce 官方材料也把 actions、guardrails、audit trail 和人工升级列为平台能力，但这些是厂商对自身产品的描述，不应直接当作所有 Agent 系统的默认能力。[3][8]

### 阶段四：交付结果或转交人工

成功答复至少需要说明三件事：系统做了什么、业务系统返回了什么、用户下一步可以做什么。不能只说“已经处理”，而应给出订单号、工单号、状态、时间或待办条件等可核对信息；如果系统没有拿到可靠结果，应明确说明未完成的部分。

转交人工不是异常兜底按钮，而是流程的一部分。以下情况通常应当触发转交或人工审批：

- 身份、授权或支付状态无法确认；
- 规则冲突，或知识源没有覆盖当前情况；
- 工具返回不完整、超时、重复或与预期不符；
- 请求涉及投诉、法律争议、重大损失、未成年人或其他高风险事项；
- 用户明确要求人工，或连续追问后仍未解决问题；
- 需要跨部门判断、特殊豁免或不可逆操作。

人工接手时，至少应看到用户目标、已确认信息、检索到的依据、调用过的工具、工具结果、失败原因和建议的下一步。Microsoft 的服务运营 Agent 文档把“保持 human in the loop”写进配置流程；这类设计可作为人工转交的参考，但转交条件和责任仍需由业务方制定。[4]

## 4. 组成 Agent 客服的能力层

Agent 客服不是一个单独的模型，而是一组相互制约的组件。

### 4.1 渠道和会话层

渠道层负责接收文字、语音或附件，维护会话身份、语言、渠道权限和历史上下文。不同渠道的身份可信度、隐私风险和可用工具可能不同，不能把网页访客、已登录用户和内部坐席当作同一种主体处理。

### 4.2 推理和编排层

编排层决定何时回答、何时检索、何时追问、何时调用工具、何时转交。可以采用单 Agent，也可以把分类、检索、订单处理和人工转交拆成多个专门 Agent。OpenAI 的 orchestration 文档把 handoffs 与 agents-as-tools 作为两种编排方式；选择哪一种，应由任务边界、权限隔离和调试成本决定。[2]

### 4.3 知识和数据层

知识层包括产品文档、服务政策、FAQ、工单历史、客户资料和实时业务数据。静态知识适合版本化管理，订单、库存、支付和物流状态则需要从业务系统实时读取。不要把所有数据复制进提示词，也不要让模型绕过正式接口直接访问数据库。

### 4.4 工具和动作层

工具层把业务能力包装成可鉴权、可审计、可测试的接口。读操作和写操作应分开；预览与提交应分开；对外发送通知、退款、注销、改签等动作应有更严格的授权、确认和审计要求。

### 4.5 人工协作层

人工协作层包括坐席工作台、队列路由、上下文摘要、审批、接管、回退和恢复。人工并不只是接收一段模型摘要，还需要看到依据和操作记录，以便判断 Agent 是否理解了问题。

### 4.6 观测和评估层

观测层记录会话、检索、工具调用、权限判断、转交和最终结果。记录应按最小必要原则处理敏感数据，并设置访问控制、保留期限和脱敏策略。OpenAI 的 evals 文档建议用评估来测试和改进模型输出；在客服场景中，评估对象应覆盖完整任务链，而不只是单句回答。[9]

## 5. 安全、隐私和治理边界

### 5.1 风险不是只有“答错”

客服 Agent 的风险包括：

- **错误知识**：引用过期政策、错误产品或错误地区的规则；
- **提示注入**：用户或外部内容诱导 Agent 忽略系统规则、泄露提示词或执行越权动作；
- **过度授权**：Agent 拥有超出任务所需的写权限，或可以调用未经过审批的工具；
- **敏感信息暴露**：在对话、日志、检索结果或转交摘要中泄露不必要的个人信息；
- **重复或不可逆操作**：重试导致重复扣款、重复建单、重复通知或错误状态变更；
- **不可解释的转交**：用户不知道为什么被转交，坐席也不知道前面发生了什么；
- **评估盲区**：只测正常问题，不测缺字段、冲突规则、恶意输入、工具超时和人工接管。

OWASP 的 LLM Top 10 将 prompt injection、sensitive information disclosure、excessive agency 等列为大模型应用风险类别。它不是客服专用标准，但可以作为工具权限、输入隔离和安全测试的风险清单入口。[10]

### 5.2 用风险管理流程组织治理

NIST AI RMF 把风险管理分为 Govern、Map、Measure、Manage 四个函数。对客服 Agent，可以对应为：

| 风险管理函数 | 客服 Agent 的落地问题 |
| --- | --- |
| Govern | 谁对模型、知识、工具、数据和人工转交负责？哪些动作需要审批？ |
| Map | 服务对象、渠道、数据、工具、副作用和潜在伤害是什么？ |
| Measure | 如何测任务完成、引用正确、工具成功、转交合理和安全事件？ |
| Manage | 发现问题后如何暂停工具、回滚版本、通知用户、复盘和重新上线？ |

这是一种实施映射，不是 NIST 对客服产品的具体规定。NIST 将 AI RMF 定位为自愿使用的风险管理框架；组织仍需结合所在地区、行业和业务合同确定合规要求。[11]

### 5.3 中国境内服务的注意事项

《生成式人工智能服务管理暂行办法》规定，向中国境内公众提供生成文本、图片、音频、视频等内容的服务适用该办法；文件要求服务提供者提高透明度、准确性和可靠性，保护输入信息和使用记录，依法处理个人信息请求，并建立投诉、举报机制。[12]

本文不据此判断某个具体客服项目是否一定属于某一监管类别。是否适用、是否需要安全评估或备案，应由法务、隐私和安全团队结合服务对象、功能、数据和部署方式确认。对于只在企业内部使用的工具、面向公众的客服服务、跨境数据处理和涉及敏感个人信息的场景，合规结论不能互相套用。

## 6. 适合和不适合的首期场景

### 6.1 适合优先试点的场景

可以优先考察以下特征：

- 请求量较稳定，问题边界清楚；
- 主要依据已经存在，并且可以按版本维护；
- 业务系统有稳定 API 或受控工具；
- 成功和失败都有明确状态；
- 失败可以回退或转交，不会造成不可逆损失；
- 结果可以在业务系统或工单系统中核对；
- 用户愿意通过当前渠道完成身份确认和必要授权。

例如，订单状态查询、配送进度说明、工单分类、资料补充提醒、预约改期预览等，通常比“自动处理所有投诉和退款”更容易定义边界。这里的“适合”只是筛选条件，不代表无需评估或一定适用于某个组织。

### 6.2 不宜作为首期自动执行的场景

以下场景更适合先做知识辅助或人工 Copilot，再逐步增加自动动作：

- 规则尚未统一，且不同地区、合同或客户等级经常产生例外；
- 需要综合判断重大财务、法律、医疗或人身安全影响；
- 工具权限难以隔离，或没有可靠的撤销和审计能力；
- 数据质量差，身份、订单、支付或合同信息经常不一致；
- 结果无法验证，或错误后无法补救；
- 组织还没有明确谁负责知识更新、模型评估和安全事件处置。

## 7. 评估指标怎么定义

不要只用“自动化率”或“回答准确率”判断 Agent 客服。建议把指标分成结果、过程、体验和风险四组，并在试点前写清口径。

| 指标组 | 指标示例 | 定义问题 |
| --- | --- | --- |
| 结果 | 任务完成率、一次解决率、转交后完成率 | 用户的目标是否真正完成？是否需要重复联系？ |
| 过程 | 检索命中率、引用正确率、工具成功率、重试率 | Agent 使用的依据和动作是否正确、稳定、可复现？ |
| 体验 | 首次响应时间、总处理时长、追问次数、人工等待时长 | 用户和坐席是否能在可接受时间内完成服务？ |
| 风险 | 越权调用、敏感信息暴露、错误承诺、重复动作、安全事件 | 系统是否在边界外做了不该做的事情？ |
| 运营 | 单会话成本、人工接管比例、知识更新时延、版本回滚次数 | 组织是否能持续维护，而不是只在演示中有效？ |

每个指标都需要分母、采样范围和人工复核规则。例如，“任务完成率”不能把只发送一条说明算作完成；应当依据业务系统状态、用户确认或人工复核判断。不同流程的目标也不应直接共用同一阈值，尤其不能把厂商案例中的比例当作本项目承诺。

## 8. 实施路线

### 第一步：选定一条服务流程

画出当前人工流程，列出入口、必要信息、知识来源、工具、审批点、成功状态、失败状态和转交队列。对每一个动作注明负责人和数据来源。若连人工流程都无法说清，不应先做 Agent 自动化。

### 第二步：建立知识和工具契约

给知识条目补充版本、有效期、适用范围和责任人；给工具补充输入校验、权限、幂等、错误码、审计字段和回滚方案。把“不能做什么”写进工具和策略，而不是只写在提示词里。

### 第三步：离线评估和人工影子运行

准备脱敏的历史请求和人工构造的边界案例，覆盖正常问题、缺字段、冲突规则、恶意输入、工具超时和人工要求。先让 Agent 只给建议，由人工决定是否执行，比较它的任务判断、检索依据、工具计划和转交理由。

### 第四步：小范围上线和逐步扩展

先开放低风险读操作或可回退动作，设置流量范围、停用开关、人工队列和日常复盘。每次扩展只改变一个变量，并保留版本、日志和评估结果。发生越权、重大错误、敏感信息泄露或不可解释的状态变化时，应能暂停相关工具，而不是只能关闭整个客服渠道。

## 9. 上线验收清单

### 业务

- [ ] 服务目标、成功状态和失败状态已经写清；
- [ ] 知识来源、版本、有效期和责任人已经确认；
- [ ] 可自动执行、需用户确认和必须人工处理的动作已经分级；
- [ ] 转交队列、坐席视图和人工接管流程已经演练。

### 技术

- [ ] 工具输入有结构化校验，读写权限分离；
- [ ] 写操作具备幂等或去重机制，失败可识别，必要时可回滚；
- [ ] 检索、工具、模型和转交事件有统一的关联 ID；
- [ ] 日志、指标和告警不收集超出必要范围的个人信息；
- [ ] 关键版本可以回放、比较和回滚。

### 安全与合规

- [ ] 已测试提示注入、越权调用、敏感信息暴露和恶意附件；
- [ ] 已确认数据处理、保留、访问和删除规则；
- [ ] 已确定投诉、举报、安全事件和人工升级的责任人；
- [ ] 已由法务、隐私和安全团队确认适用的监管和合同要求。

### 评估

- [ ] 指标有明确分母、采样方法和人工复核规则；
- [ ] 测试集包含正常案例和边界案例，且不会只测模型熟悉的问法；
- [ ] 每次知识、工具、模型或策略变更都有回归评估；
- [ ] 上线后能够识别错误承诺、重复动作、越权调用和不合理转交。

## 10. 结论

Agent 客服适合被当作一套受控的服务执行系统，而不是一个更会聊天的 FAQ。它的基本流程是：理解目标，找到依据，调用有权限的工具，检查业务结果，向用户交付或把上下文交给人工。任何一个环节缺少边界，系统就可能只是在生成看起来合理的回答，无法稳定完成服务任务。

首期实施的验收标准也应从“回答像不像人”转向“任务是否完成、依据是否可查、动作是否可控、失败是否可恢复”。先把一类请求完整处理，再扩展到更多流程，是便于评估、审计和复盘的起点。
