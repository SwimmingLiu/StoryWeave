# Agent 客服一手资料研究

> 研究日期：2026-08-20。本文为后续 Agent 客服材料和 HTML 演示提供事实底稿。资料优先采用官方文档、标准组织文件、监管文件和厂商一手产品文档。厂商文档中的能力描述只代表厂商对产品的说明，不等于独立性能证据。

## 研究口径

“Agent 客服”目前没有一个可直接套用的统一法律定义。本文把它作为一个方案术语：系统接收客户目标，在权限和业务规则约束下，调用知识检索与业务工具，推进一个或多个服务步骤，并在需要时把完整上下文交给人工。这个定义是基于 OpenAI 对 Agent 运行方式的描述、Google 对虚拟 Agent 与数据存储的说明，以及客服产品的公开能力归纳而来，不是某一家厂商的标准定义。[S1][S2][S9][S12][S15]

文中区分四类信息：

- **已确认事实**：可由来源原文直接核对。
- **厂商能力描述**：产品文档或产品页声称能够提供的能力，不能据此推导实际准确率、成本或客户收益。
- **方案判断**：根据事实提出的工程设计建议。
- **待核验事项**：需要结合具体行业、地区、数据、合同、接口和实测结果确认的内容。

本文没有使用虚构的客户案例、用户反馈、响应时间、成本下降比例或效率提升比例。

## 结论摘要

Agent 客服与 FAQ 页面或单轮问答的区别，在于它可以围绕一个服务目标持续推进：理解请求，检索相关知识，调用业务系统，检查工具结果，给出下一步，并在边界条件触发时转交人工。OpenAI 的 Agents SDK 文档把 Agent 描述为能够规划、调用工具、协作并保留足够状态以完成多步骤工作的应用；其运行循环会在模型调用、工具调用、Agent 交接和最终回答之间继续执行。[S1][S6]

客服场景中的自动化边界应按动作风险划分。查询订单状态、解释公开政策、生成工单摘要通常可以先从只读能力开始；退款、取消、改址、改价、修改账户或向外发送信息属于有副作用的操作，需要业务系统再次授权、参数校验、幂等控制、审计记录，并根据风险决定是否需要用户或人工审批。[S2][S5][S18]

知识检索不能替代知识治理。OpenAI 的检索文档说明语义检索可以找到关键词重合很少的相关内容；Google Dialogflow CX 的数据存储文档说明 Agent 会搜索来源内容、总结回答并提供来源链接，同时支持按文档保存 ACL、只返回当前用户有读取权限的实体。[S3][S4][S10]

评估应同时覆盖回答、检索、工具和转交。OpenAI 建议先用 Trace 查看一次运行的模型调用、工具调用、Guardrail 和 handoff，再用数据集和评测运行形成可重复的比较；Microsoft Copilot Studio 把测试用例、测试集、期望答案、工具使用和可重复运行作为评估机制，同时明确评估不能替代安全与负责任 AI 审查。[S7][S8][S14]

## 1. Agent 客服是什么

### 1.1 由一条回答扩展为服务任务

OpenAI 的 Agents SDK 文档给出的能力组合包括：规划、工具调用、专家协作和状态保存。其运行循环会先调用当前 Agent，再检查模型输出；如果输出包含工具调用，就执行工具并继续；如果发生 handoff，就切换到另一个 Agent；没有更多工具工作时才返回结果。[S1][S6]

OpenAI 的函数调用文档把模型和业务系统的边界写得很清楚：模型提出工具调用，应用侧执行代码，再把工具结果发回模型。完整流程包括提供工具、接收工具调用、应用侧执行、回传工具结果、接收最终回答或下一轮工具调用。工具的真实权限和副作用仍由应用代码和下游系统负责。[S2]

Google Dialogflow CX 将 Agent 描述为能够处理与最终用户的并发会话的虚拟 Agent，并说明它与人工呼叫中心 Agent 类似。这个描述说明了客服产品中的对话承接方式，但不意味着它自动拥有访问订单、账户或退款系统的权限；那些能力仍取决于配置的工具、数据源和下游授权。[S9]

Salesforce 的 Agentforce 产品页把 AI Agent 描述为面向员工和客户执行专门任务的自主、主动式应用，并声称产品可以使用可信业务数据、执行动作，在超出范围时升级到人工。由于这是厂商产品页，本文只把它作为产品能力和行业术语的实例，不把“自主”或“高效”解释为已验证的性能结果。[S15]

基于这些来源，本文采用如下工作定义：

> **Agent 客服是围绕客户服务目标组织的一套受约束的 Agent 工作流。它可以读取经过授权的知识和业务数据，调用粒度明确的工具推进任务，记录过程和结果，并在不确定、有风险或超出范围时转交人工。**

### 1.2 与相邻形态的区别

| 形态 | 主要输出 | 是否推进业务动作 | 典型边界 |
| --- | --- | --- | --- |
| FAQ / 知识库 | 文章、答案、来源链接 | 通常不推进 | 依赖内容质量和检索权限；不能把检索命中等同于事实正确 |
| 脚本式聊天机器人 | 按固定意图和流程对话 | 可以调用预定义流程 | 对未覆盖表达和流程外请求处理有限；是否使用大模型取决于具体产品 |
| RPA / 工作流自动化 | 固定步骤的系统操作 | 可以推进确定性动作 | 通常依赖明确字段和规则；不负责开放式理解与解释 |
| 人工客服 | 判断、沟通、授权和例外处理 | 可以 | 成本、时段、并发和信息转移需要单独管理 |
| Agent 客服 | 回答、检索、规划、工具调用、转交和过程记录 | 可以，在授权范围内 | 必须把模型的不确定性、工具权限、审批和审计纳入设计 |

表中的分类是方案层面的比较，不是某个标准组织发布的分类。实际产品可能同时包含多种形态。例如，Google 数据存储可以支持 FAQ 数据，而 Microsoft Customer Service Agent 同时提供检索、摘要和案例动作。[S10][S12]

## 2. 能力组成

### 2.1 知识检索与来源约束

OpenAI File Search 是 Responses API 中的托管工具。官方文档说明，它可以从已上传到向量存储的文件中通过语义和关键词搜索检索信息；模型决定使用该工具后，平台会执行检索并返回结果。[S3]

OpenAI Retrieval 文档进一步说明，语义检索使用向量嵌入找到语义相关内容，即使结果与查询几乎没有共同关键词，也可能被找到；搜索结果包含相关文本块、相似度分数和来源文件。[S4]

Google Dialogflow CX 的 Data stores 文档说明：

- 数据存储供 data store tools 从指定数据中寻找最终用户问题的答案。
- Agent 搜索来源内容后，可以把发现内容总结成连贯回答，并向用户提供来源链接。
- FAQ 数据存储可以为问答对提供标题和 URL；文档说这类答案可以直接展示。
- 对部分第三方数据源，每份文档会保存 ACL；回答只会使用当前用户有读取权限的实体。文档还提供数据存储执行追踪，包括查询重写、grounding 检查、安全检查和搜索片段。[S10]

这些文档支持的工程结论是：知识库应该被当作有版本、有权限、有来源的业务数据，而不是一段放进 Prompt 的静态文本。建议为每条知识至少记录来源、版本、生效时间、失效时间、适用产品/地区、访问范围和维护责任人；检索结果应携带来源标识，回答无法由可靠来源支撑时应明确说明无法确认。[S3][S4][S10]

OWASP LLM08:2025 指出，向量和嵌入系统可能出现未授权访问、跨上下文泄露、数据投毒和行为改变等风险，并建议使用权限感知的向量存储、验证知识来源、对组合数据做分类审查，以及记录不可篡改的检索日志。[S19]

### 2.2 工具调用与业务系统连接

函数调用可以把“查账户详情”“查询订单”“检查退款资格”等业务能力以结构化 Schema 提供给模型。OpenAI 文档明确要求应用侧接收调用、执行代码并回传结果；这意味着模型只是在选择和填写参数，真正的授权、数据访问、事务提交和错误处理不能放在自然语言指令中。[S2]

Salesforce Agentforce 产品页列出的构建方式包括标准或自定义 subagent、actions、Flows、MuleSoft API connectors，以及 Apex 和 JavaScript 自定义逻辑。这个例子说明商业产品通常把 Agent 连接到已有业务编排和 API 层，而不是让模型直接访问数据库。[S15]

Microsoft Dynamics 365 Customer Service 文档说明，相关 Agent 可以使用组织的客户服务数据，例如案例、客户记录和交互，帮助代表查找信息、总结上下文并在工作流中采取动作；其 Service Agent 示例包括检索案例详情、生成摘要、更新案例和创建后续任务。[S12]

方案上，工具应满足以下约束：

- **粒度明确**：优先提供 `get_order_status`、`check_refund_eligibility` 这类有固定输入输出的工具，避免提供“执行任意 SQL”或“调用任意 URL”这类开放式能力。
- **读写分离**：读取订单和修改订单应是不同工具，不要让只读场景继承写权限。
- **服务端授权**：下游系统每次请求都重新校验用户、租户、角色、资源归属和参数范围，不能只依赖 Agent 自己判断是否允许。
- **副作用控制**：写操作要有幂等键、状态检查、超时、重试策略和可回滚路径；返回结果应包含业务系统确认的状态，而不是只返回“已完成”的自然语言。
- **记录调用**：保存调用者、工具版本、参数摘要、授权结果、执行结果、错误和关联会话 ID，同时对敏感参数做脱敏。

### 2.3 状态、上下文与任务连续性

OpenAI Agents SDK 提供多种状态承载方式，包括应用侧历史、SDK session、Conversations API 和 Responses API 的 previous response ID。文档建议一个会话选择一种主要策略，避免同时重放本地历史和服务端状态造成上下文重复。[S1][S6]

客服系统需要把至少三种状态分开：

1. **会话状态**：当前对话中的问题、已确认的字段和用户意图。
2. **业务状态**：订单、工单、预约或退款在权威业务系统中的真实状态。
3. **审批状态**：某个动作是否等待用户、主管或人工客服批准。

第二类状态不能由模型记忆代替。用户说“刚才已经改好了”时，Agent 仍应查询业务系统；审批等待期间恢复运行，也应从原来的可恢复状态继续，而不是新建一个看似相同的请求。[S2][S5][S6]

### 2.4 人工转交与失败处理

OpenAI 的 Orchestration 文档区分两种多 Agent 模式：handoff 表示控制权转移给专业 Agent；agents-as-tools 表示主管 Agent 保持最终回答权，把专业 Agent 当成受限能力调用。文档建议只有在下一分支确实需要不同指令、工具或策略时才拆分专业 Agent。[S6]

OpenAI Guardrails and human review 文档把人工审核定义为：工具调用在产生副作用前暂停，返回可恢复的 state 和 interruption，应用完成批准或拒绝后从同一个 state 继续运行。文档把取消、编辑、敏感 MCP 操作等列为需要考虑审批的动作。[S5]

Salesforce Agentforce 产品页声称，当问题超出 Agent 范围时可以升级给人工；这是一项厂商产品能力描述，实际转交条件、队列、上下文格式和渠道支持仍需在目标产品中验证。[S15]

一个可执行的人工转交策略至少应包括：

- 用户明确要求人工，或连续多次无法识别/解决请求。
- 知识检索没有足够证据、来源冲突或业务数据不可用。
- 请求涉及高金额、高影响、身份变更、投诉、争议、法律/医疗/金融判断或其他组织规定的高风险操作。
- Agent 需要执行写操作但没有得到所需批准，或者工具返回异常。
- 发现疑似 Prompt Injection、越权访问、数据泄露或账户盗用迹象。

转交给人工时，应一并传递用户身份和授权范围、会话摘要、已验证事实、检索来源、已执行工具及结果、未完成步骤、风险提示和用户已表达的偏好。转交本身也要成为可查询的事件，而不是只在前端换一个队列。

### 2.5 观测、评测与指标

OpenAI Agents SDK 的 tracing 可以记录一次运行中的模型调用、工具调用、handoff、guardrail 和自定义 span。OpenAI 的评测文档建议先通过 trace grading 定位工作流问题，再使用数据集和重复评测比较 Prompt、工具表面、路由和 Guardrail 的变化。[S7][S8]

Microsoft Copilot Studio 的 Agent evaluation 文档明确说明：测试用例可以是一次问题或完整对话；测试集可以重复运行，并将回答与期望回答或质量标准比较；评估可测量准确性、相关性和质量，也可以检查工具使用。Microsoft 同时明确指出，Agent evaluation 衡量正确性和性能，不等于伦理或安全审查，不能替代负责任 AI 审查和内容安全过滤。[S14]

Google Dialogflow CX 的测试用例文档支持保存对话中的预期结果，之后重复运行并查看测试结果；它还提供基于 transitions、intents 和 route groups 的测试覆盖率。[S11]

以下指标可作为项目的测量框架。它们是建议的定义，不是行业统一阈值：

| 指标 | 建议定义 | 需要保留的证据 |
| --- | --- | --- |
| 任务完成率 | 在预先定义的测试集或真实抽样中，业务系统确认目标状态已达成的比例 | 请求 ID、业务状态变更、失败原因 |
| 有依据回答率 | 回答中的可验证陈述能够对应到允许使用的知识来源或业务查询结果的比例 | 来源 ID、片段、查询时间、回答版本 |
| 检索有效率 | 相关知识进入候选结果并被正确使用的比例，可按问题类型分层 | 查询、候选片段、人工标注或期望来源 |
| 工具调用成功率 | 工具参数通过校验且下游系统返回成功状态的比例 | 工具版本、参数校验、下游状态、重试次数 |
| 错误动作率 | 不应发生的写操作、错误对象操作或越权访问尝试的比例 | 授权日志、策略命中、审计事件 |
| 转交适当性 | 应转交的请求是否转交、无需转交的请求是否被错误转交 | 转交规则、人工复核标签、上下文完整度 |
| 首次解决率 | 不需要再次追问、重开或人工接管就完成的请求比例 | 会话和工单关联、重开时间窗 |
| 延迟与成本 | 按场景统计从请求到可用结果的时间、模型/工具调用成本 | 分阶段时间戳、Token/调用量、费用 |
| 安全与隐私事件 | Prompt Injection、敏感信息泄露、越权、违规内容和审计缺失的数量与严重度 | 事件分类、影响范围、处置记录 |

验收时应把成功率按场景、语言、渠道、租户、身份状态和风险等级分层，不用一个总体平均数掩盖高风险场景。任何“减少人工”“提升效率”“全天候服务”的表述，都应在材料中标为目标或厂商宣传，除非有可复现的基线、样本、时间窗口和审核方法。

## 3. 权限、隐私、审计与安全

### 3.1 Prompt Injection

OWASP LLM01:2025 将 Prompt Injection 定义为：用户提示改变大模型行为或输出，导致结果偏离预期；间接注入还可能来自网页、文件或其他外部内容。该项目列出的影响包括敏感信息披露、未授权访问模型可用功能、执行连接系统中的任意命令以及影响关键决策。OWASP 明确表示，RAG 和微调不能完全消除这类漏洞。[S16]

OWASP 的缓解建议包括限制模型行为、校验输出格式、输入输出过滤、最小权限、对高风险动作要求人工批准、隔离并标记不可信内容，以及持续进行对抗测试。对客服 Agent 的直接含义是：客户消息、上传文件、检索片段和第三方网页都不能自动拥有系统指令的地位；工具边界必须由代码和下游授权强制执行。[S16]

### 3.2 Excessive Agency 与最小权限

OWASP LLM06:2025 把 Excessive Agency 描述为：模型因为功能过多、权限过大或自主程度过高，在意外、含糊或被操纵的输出下执行有害动作。它特别建议减少扩展数量和功能、避免开放式工具、限制下游权限、在用户上下文中执行、要求高影响动作审批，并在下游系统实施完整授权，而不是依赖大模型决定是否允许。[S18]

因此，客服 Agent 的权限矩阵应至少区分：

| 资源/动作 | 默认权限 | 需要的额外控制 |
| --- | --- | --- |
| 公开政策和产品说明 | 读取 | 来源版本、适用地区和生效时间 |
| 当前用户自己的订单/工单 | 按用户身份读取 | 租户隔离、对象归属校验 |
| 订单状态查询 | 只读 | 参数白名单、限流、审计 |
| 退款资格计算 | 只读或预演 | 业务规则版本、金额和币种校验 |
| 退款、取消、改址、改价 | 默认不自动执行 | 用户确认、人工审批或双重校验、幂等键 |
| 向外部发送邮件/消息 | 默认不自动执行 | 预览、收件人校验、明确批准、留痕 |
| 任意数据库、任意 URL、任意命令 | 禁止暴露给模型 | 改造成粒度明确的服务端工具 |

这是方案建议，不是某家产品的默认配置。

### 3.3 敏感信息与检索数据

OWASP LLM02:2025 将个人身份信息、金融信息、健康记录、商业机密、凭证和法律文件列为敏感信息，并指出模型应用可能在输出中泄露这些数据。其建议包括输入清洗、严格访问控制、限制外部数据源、明确数据保留和删除政策，以及对用户说明数据如何使用。[S17]

OWASP LLM08:2025 进一步指出，向量数据库中的权限错配可能造成跨租户或跨上下文泄露；知识源也可能被投毒，导致检索结果操纵模型输出。建议对知识源做来源认证和定期审查，给数据分类，并保留检索活动的不可篡改日志。[S19]

客服系统的最低数据控制包括：

- 只收集完成当前服务所必需的字段，敏感字段尽量在进入模型前脱敏或令牌化。
- 在检索阶段应用租户、用户、角色和对象归属过滤，而不是检索后再靠 Prompt 让模型“不要泄露”。
- 训练、评测、Trace、客服质检和生产会话分别定义访问范围、保留期限和删除流程。
- 审计日志记录必要的事实，不把完整身份证号、支付凭证或健康信息直接写入每个日志字段。
- 对模型供应商、向量数据库、客服平台、API 连接器和人工坐席工具逐一核对数据处理、地域、保留、子处理者和跨境条款。

### 3.4 审计与可观测性

OpenAI 文档把 trace 作为调试和评测 Agent 工作流的记录；Microsoft Copilot Studio 安全与治理文档则说明其产品覆盖地理数据驻留、DLP、合规和审计相关能力，并提到 Agent 调用、工具/动作调用、策略决定和运行时信号可以进入 Microsoft Purview audit logging pipeline。这些是平台能力说明，不能代替项目自身对日志内容、权限和保留策略的验证。[S7][S13]

建议对每个请求建立可关联的事件链：用户身份和授权版本、输入摘要、检索查询和来源、模型与 Prompt 版本、工具调用和参数摘要、策略/审批结果、下游系统确认、回答、转交、人工处理和最终业务状态。审计设计应同时满足排障、质检、安全事件调查和个人信息删除请求，避免为了“留全量日志”而无限期保存敏感内容。

### 3.5 风险治理框架与中国境内公开服务边界

NIST AI Risk Management Framework 页面说明，AI RMF 旨在帮助组织把可信性因素纳入 AI 产品、服务和系统的设计、开发、使用与评估；该框架为自愿使用。NIST AI RMF Playbook 按 Govern、Map、Measure、Manage 四个功能组织建议。[S20]

可将四个功能映射到客服 Agent：

- **Govern**：明确产品负责人、数据负责人、风险审批人、供应商责任和停止服务条件。
- **Map**：画清用户、模型、知识库、工具、人工队列和下游业务系统之间的数据流与风险。
- **Measure**：用代表性测试集、对抗样本、真实抽样和人工复核测量回答、工具、转交和安全表现。
- **Manage**：按风险优先级修复、限制发布范围、保留回滚路径并持续复盘事件。

中国国家互联网信息办公室发布的《生成式人工智能服务管理暂行办法》规定，向中华人民共和国境内公众提供生成文本、图片、音频、视频等内容的生成式人工智能服务适用该办法；未向境内公众提供生成式人工智能服务的研发、应用活动不适用该办法的相应规定。[S21]

该办法对公开服务提出的相关要求包括：

- 训练数据和基础模型应具有合法来源；涉及个人信息的，应取得个人同意或符合其他法定情形。
- 提供者对使用者输入信息和使用记录承担保护义务，不得收集非必要个人信息，不得非法留存或向他人提供可识别身份的输入和记录。
- 提供者应依法处理查阅、复制、更正、补充、删除个人信息的请求。
- 服务应提升透明度，提高生成内容的准确性和可靠性，并建立投诉、举报入口、处理流程和反馈时限。
- 发现违法内容或违法使用时，应采取停止生成、停止传输、限制功能、暂停或终止服务等处置措施，并按规定保存记录和报告。

这些规定是否适用于某个 Agent 客服，取决于它是否向境内公众提供相关生成式人工智能服务、部署主体、处理的数据和行业监管要求。本文不是法律意见；上线前应由法务和安全团队按渠道、地区、行业和合同逐项确认。[S21]

## 4. 适用场景与不适用边界

### 4.1 适合优先验证的场景

适合首期验证的流程通常同时满足：政策相对稳定、已有结构化 API、结果可由业务系统确认、失败后能够转交人工、写操作风险可控。例如：

- 公开政策、产品说明、营业时间和流程指引的检索回答。
- 订单、工单、物流或预约状态查询。
- 根据明确规则检查退款或换货资格，并把结果交给用户确认。
- 收集工单必要字段、分类、摘要和路由。
- 为人工客服生成带来源和业务事实的会话摘要。

这些是按风险和可验证性提出的方案建议，不代表任何供应商保证在所有数据和渠道中达到相同效果。

### 4.2 需要谨慎或暂不自动化的场景

以下场景不宜在缺少额外控制时直接交给 Agent 完成：

- 不可逆或高金额的退款、取消、账户关闭、身份和收款信息变更。
- 需要专业判断或法定责任的医疗、金融、法律、保险和安全事件处理。
- 依赖情绪识别、价值判断、例外裁量或事实争议的投诉与纠纷。
- 知识来源不稳定、权限边界不清、下游 API 没有幂等或审计能力的流程。
- 不能向用户提供人工转交、申诉、纠错和删除渠道的服务。

## 5. 实施路线与验收清单

### 5.1 分阶段路线

1. **界定范围**：选定一个具体服务流程，写出成功状态、失败状态、禁止动作、人工转交条件和停止服务条件。
2. **治理知识**：清理来源，建立版本、生效期、适用范围、权限标签和维护责任；为冲突、缺失和过期内容定义处理规则。
3. **先接只读工具**：接入订单、工单或预约查询，验证身份、租户隔离、检索来源、超时和错误处理。
4. **加入受控写操作**：把写动作拆成粒度明确的工具，增加参数校验、幂等键、用户确认或人工审批，并在业务系统中做最终授权。
5. **接入人工处理流程**：实现带摘要、证据、工具结果和风险提示的转交；记录转交原因和人工最终处理结果。
6. **持续评测**：建立覆盖正常、边界、对抗、权限和多轮场景的测试集；每次更新模型、Prompt、知识、工具或策略后重跑，并把真实事件回灌到测试集。

### 5.2 上线前验收

- 业务：每个工具有固定 Schema、责任系统、成功状态、失败状态和回滚/补偿方案。
- 权限：已验证登录、租户隔离、对象归属、最小权限、读取与写入分离。
- 知识：每个回答场景有允许的来源、版本和失效规则；无依据时有明确拒答或转交路径。
- 人工：用户可主动要求人工；高风险、无法确认、工具失败和越权迹象能够自动转交。
- 安全：完成直接/间接 Prompt Injection、数据泄露、越权、知识投毒、重复提交和重放攻击测试。
- 审计：可以从会话 ID 追到检索、模型、工具、审批、下游状态、回答和转交；敏感字段有脱敏和删除方案。
- 评测：有固定测试集、分场景指标、人工抽检、回归门槛和发布回滚机制；安全评审不被回答分数替代。
- 合规：已按部署地区、公开/内部属性、行业要求、数据处理主体和供应商合同完成法务及安全核验。

## 7. 待进一步核验

- 目标 Agent 客服的服务对象、部署地区、是否向中国境内公众开放，以及是否落入行业监管或许可范围。
- 真实知识源的所有权、版本、保密等级、个人信息字段、跨租户边界和失效机制。
- 每个业务工具的身份传递、OAuth/服务账号范围、下游授权、幂等、事务一致性和审计字段。
- 人工队列、转交渠道、客服工作台、服务级别协议和用户申诉/删除入口是否可以保留同一会话上下文。
- 模型供应商、向量存储、客服平台和连接器的数据保留、训练用途、区域、跨境和子处理者条款。
- 测试集的代表性、人工标注一致性、对抗样本覆盖、分场景门槛，以及从灰度到全量的回滚条件。
